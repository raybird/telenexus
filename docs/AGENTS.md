# 文件資料夾說明（AGENTS）

本檔是下游專案 issue 流程的入口。一般局部修改依專案規則直接執行；使用者要求追蹤 issue 或啟動開發閉環時，才建立本規範的文件。

## 客製邊界與同步策略

上游核心放在本檔與 `agents/` 參考檔；專案內容集中於 `agents/project.md`，每次規劃與交付前讀取。核心欄位與狀態依本規範使用，專案可在 project.md 指定目錄、規模門檻、驗證命令、提交格式與額外 gate；專案規則不得把未執行的驗證當成通過。

| 需要做的事 | 必讀材料 |
|---|---|
| 決定文件數量、任務來源、驗證順序 | 本檔「文件動態分級規範」 |
| 澄清、核准、修訂驗收條件 | [agents/acceptance.md](agents/acceptance.md) |
| 執行、查核測試或觀測證據 | [agents/verification.md](agents/verification.md) |
| 建立 PR、review、判定審查是否仍有效 | [agents/review-evidence.md](agents/review-evidence.md) |
| 決定文件內容、建立或更新 README | [文件類型](agents/document-types.md)、[README 範本](agents/readme-templates.md) |
| 完成 new-issue | [issue 檢查清單](agents/issue-checklist.md) |
| 規劃、驗證、提交或更新常青文件 | [專案客製規範](agents/project.md) |

部署時包含整個 `docs/agents/` 與 `docs/_templates/`。`init-project.py` 記錄上次部署檔案的雜湊於 `docs/.dev-rules-kit.json`；`--update` 只更新未被本地改寫的上游檔案，既有 project.md 保持原樣。雜湊只用於部署衝突判斷，不是驗收核准證據。

舊專案首次遷移：先把目錄樹、常青文件對照、命令、案例與本地 gate 移到 project.md，人工合併本次核心變更，再執行初始化建立部署基線。沒有可信基線的不同檔案會停止更新，不猜測其來源。已移除的上游檔案不自動刪除，依版本說明處理。

### 核心層齊備性檢查

- **文件版本**記錄編輯版本；純措辭與範例更新不改變流程契約。
- **流程契約**使用 major.minor：major 表示不相容語意或結構變更；minor 表示向後相容的新增能力。skill 宣告最低需要的流程契約，同 major 且專案 minor 不低於需求才相容。
- 先讀本檔的契約版本，再確認此次分支所引用的材料、章節與欄位齊備。缺漏、major 不符、minor 太舊或語意衝突時，列出具體落差與遷移方式；暫停依賴該契約的操作，其餘唯讀分析可繼續。
- 查詢模式只回報落差；推進時若已授權更新，先準備可檢視的遷移，再依安裝器衝突保護更新。需要決定本地語意時才詢問。

核心介面維持：`**分級**`、`**風險**`、`**狀態**`、`**核准 commit**`；核准狀態 `已核准`／`待核准`／`待重新核准`；review 判定 `PASS`／`RETURN TO execute-task`／`UNPERSISTED`。核准與證據細節只在上表對應材料定義。

## 核心設計原則：YAGNI (You Ain't Gonna Need It)

在評估任務與建立文件時，Agent 必須嚴格遵守 YAGNI 原則：

1. **拒絕通靈需求**：僅針對當前 Issue 明確定義的範疇進行分析與規劃。嚴禁為了「未來可能擴充」而規劃超出範疇的資料庫 Schema、API 欄位或系統架構。
2. **文件量隨變更規模走**：嚴格執行下方的「文件動態分級規範」，每份文件的每個章節都要承載這次變更實際產生的內容。
3. **保持最小範疇**：在 README 的 `## 涉及檔案` 中，僅列出完成此任務「絕對必要」的涉及檔案，評估範圍到此為止。

## 文件動態分級規範 (Issue Document Tiering)

> **本節是 issue 規模與風險規則的唯一權威定義（single source of truth）。** `new-issue`、`dev-cycle`、`execute-task`、`decompose` 等 skill 內的說明皆為方便閱讀的摘要，若有出入一律以本節為準；調整規則時必須先改本節，再檢查各 skill 的引用與 gate。

Issue 必須分別評估兩個互不推導的軸：

- **規模（`**分級**`）**：只決定文件數量、任務清單來源及是否需要 `decompose`。
- **風險（`**風險**`）**：只決定實作順序、首要驗證手段及必要證據，不改變文件數量。

### 規模分級

為了在保障開發正確性的同時避免「小變更、重文件」的繁重負擔，文件產生應依任務複雜度動態評估（Small / Medium / Large 三級），只產出對應的必要文件：

| 分級 | 適用場景 | 產出檔案 |
|------|---------|---------|
| **輕量級 (Small)** | 單一檔案的 Bug 修正、極簡單的 feature 實作、文字/日誌/設定微調 | 僅 **`README.md`**（需求與實作步驟皆合併寫在 README 內，不另建分析與計畫檔案） |
| **中量級 (Medium)** | 局部功能的 Feature 開發、不涉及複雜架構調整的重構、多檔案但邏輯直觀的修改 | **`README.md`** + **`implementation-plan.md`**（分析併入實作計畫的前置章節，省略單獨分析文件） |
| **重量級 (Large)** | 跨多個模組/服務、新增資料庫 schema、複雜系統遷移、重大架構變更或大型功能模組開發 | **`README.md`** 與 **`implementation-plan.md`**；`requirement-analysis.md` 與 `technical-analysis.md` 依下方觸發條件建立 |

Large 的兩份分析文件各自回答一個 README 與 implementation-plan 都答不了的問題，**在該問題實際存在時才建立**：

| 文件 | 建立條件 |
|------|---------|
| `requirement-analysis.md` | 需求範圍或現況行為有需要調查才寫得下來的部分——`## 待確認事項` 有影響需求範圍的項目，或現況行為必須讀既有程式碼才能確定 |
| `technical-analysis.md` | 澄清過程提出了兩個以上方案並做了取捨，取捨理由需要留給後續讀者 |

`## 文件清單` 只連結實際建立的文件。**每一份未建立的分析文件，都答得出它的觸發條件為何不成立**——答不出來就是該建。條件隨實作推進才成立時（例如中途才出現需要取捨的方案），當下補建。

分級一經評估，**必須寫入 `README.md` 結尾 metadata 的 `**分級**` 欄位**，值以 `Small`、`Medium`、`Large` 開頭（後面可接補充說明，判定只看開頭的詞）。**這是後續流程唯一可靠的分級來源**——缺欄位時只能依檔案形狀回推，而 Large 未建分析文件時的形狀與 Medium 相同，回推無從區分：

| 分級 | 任務清單來源 | 是否需要額外拆解 |
|------|-------------|----------------|
| **Small** | `README.md` 的「實作與驗證步驟」 | 否 |
| **Medium** | `implementation-plan.md` 的「實作步驟」 | 否 |
| **Large** | `implementation-plan.md` 內的 Phase / Task | 是 |

Small 與 Medium 的實作步驟本身即為可執行的任務清單，**直接以該清單作為任務來源**（同一份步驟只寫一遍）。僅 Large 因跨模組、任務量大，才需要進一步拆解為 Phase / Task。

### 風險分級

風險一經評估，**必須寫入 `README.md` 結尾 metadata 的 `**風險**` 欄位**：

| 風險 | 判定原則 | 規劃要求 |
|------|---------|---------|
| **Low** | 行為與依賴明確、影響侷限、容易回復 | 可依一般相依順序實作與驗證 |
| **Medium** | 存在一項重要未知，或失敗會造成有限度返工與影響 | 將降低該風險的驗證排在主要實作前 |
| **High** | 涉及資料損失、安全或權限、不可逆操作、廣泛影響，或核心外部行為尚未確認 | 第一個步驟或 Phase 必須先取得能解除最大風險的證據 |

不採加總分數。只要符合較高等級的任一關鍵條件，就採較高風險，並記錄判定理由。**規模與風險不得互相推導**：Small + High 仍只產出 README、仍使用輕量驗收條件（強度另依「驗收標準的形式依規模決定，強度依風險決定」加強）；Large + Low 仍依 Large 的文件規則、仍使用完整 Gherkin 並執行 `decompose`。分析文件的觸發條件看的是「有沒有需要調查的需求或做過的取捨」而非風險等級——兩者常一起出現，判定依前者。

### 風險優先決策流程

規劃實作步驟或 Phase 時，必須依序完成：

1. 指出最大的未驗證假設或最嚴重的失敗後果。
2. 判定 Low、Medium 或 High，並寫出理由。
3. 根據風險來源選擇首要驗證手段。
4. 定義可判定風險已解除或降至可接受程度的證據。
5. 完成上述判斷後，才排列後續實作步驟或 Phase。

風險為 Medium / High 時，文件必須明確記錄「最大風險」、「風險等級與理由」、「首要驗證」、「選擇理由」與「完成證據」五項。Low 且無特殊前置驗證時，`## 風險與首要驗證` 可收斂為一行——`**風險**: Low — 無明顯未知，依一般相依順序實作與驗證`——不逐欄填寫五項樣板；實作中升級為 Medium / High 時再展開完整五項。

| 風險來源 | 優先手段範例 |
|---------|-------------|
| 外部 API、套件或服務契約未知 | 契約驗證、最小真實請求、相容性探測 |
| 既有資料樣態未知 | 資料盤點、分布查詢、小樣本 dry run |
| 效能或容量未知 | 基準測試、壓力測試、最小技術實驗 |
| 害怕破壞既有行為 | Characterization test、快照、對比腳本、回歸測試網 |
| 使用者流程或跨層整合未知 | 垂直切片，端到端跑通最窄可驗證路徑 |
| 行為、資料與依賴皆明確 | 依一般技術相依順序實作 |

此表是候選手段，不是固定對照。**順序是先指出最大的未驗證假設，再由它決定手段。** 垂直切片適用於「端到端整合或使用者行為是最需要驗證的假設」這一種情況，與表中其他手段平級。

選擇垂直切片時必須回答：

1. 此切片要驗證哪一項尚未確認的端到端假設？
2. 為何契約驗證、資料盤點、效能實驗或回歸保護網不能更直接降低該風險？
3. 切片完成後，要觀察到什麼證據才算假設已獲驗證？

若無法回答，應重新選擇首要驗證手段。


## BDD 驗收規格與 TDD 證據

建立或修訂驗收規格時讀 [acceptance.md](agents/acceptance.md)；實作、驗證或判斷假綠燈時讀 [verification.md](agents/verification.md)。review artifact 與 PR 證據依 [review-evidence.md](agents/review-evidence.md)。

## Gate 豁免紀錄

使用者明確要求跳過 gate 時，在 issue README 的 `## Gate 豁免紀錄` 記錄日期、豁免項目、使用者原話與殘餘風險。只豁免明列項目；已記錄的授權持續有效。不得將未執行的驗證或獨立審查寫成已通過。

## 待確認事項

不影響安全範圍與首要驗證的未知，集中於 README 的 `## 待確認事項`：

| 編號 | 事項 | 狀態 | 影響 |
|---|---|---|---|
| TBD-1 | 等待的資訊或決策 | 待確認 | 影響及關聯驗收編號 |

編號穩定不重編；狀態為 `待確認`、`已解決`、`不影響本次交付`，後兩者需結論、理由與日期。待核准 Scenario 必須有對應項目。非阻塞未知可在 PR 揭露後交由 reviewer 評估；影響安全範圍或必要驗證者先解決。無項目時整節省略。

## 合法的中間狀態與終態

| `**狀態**` | 必須記錄 | 推進方式 |
|---|---|---|
| `等待外部驗收窗` | 預定窗口、待觀察判準、窗口前工作已完成的證據 | 窗口未到則回報並結束本次調用；窗口到達才執行待觀察項目 |
| `不修復` | 判定來源與理由、殘餘影響、追蹤方式或不再追蹤理由 | 覆核決策紀錄後保留此終態；不要求實作或 merge 證據 |
| `已完成` | 已合併 PR 或明確核准的其他結案依據 | 依實際結案方式記 Timeline；只有真實 merge 才記 merge 日期 |

等待狀態只涵蓋確實要等待的工作，不能遮蔽當下可完成的驗證。不修復需獨立 reviewer 覆核決策，或記錄該 gate 的明確豁免；沒有程式變更時不要求程式測試。已合併 issue 的歷史核准 SHA 不再作為實作 gate。

## Issue 資料夾命名

- **格式**：`issues/issue-{編號}/`
- **範例**：`issues/issue-0101/`、`issues/issue-0102/`（編號沿用專案 issue tracker 的實際編號）

## 文件類型與內容規範

各文件（`README.md`、`requirement-analysis.md`、`technical-analysis.md`、`implementation-plan.md` 及其他專項文件）的用途、標記與應包含的內容，見 [`agents/document-types.md`](agents/document-types.md)。是否建立某份文件由上方「文件動態分級規範」決定，本節只規定建立後該寫什麼。

## README.md 範本

建立 issue README 時套用 [`agents/readme-templates.md`](agents/readme-templates.md)：Medium / Large 用標準格式（含文件清單、Gherkin 驗收劇本與核准紀錄、風險與首要驗證、Timeline、metadata），Small 用輕量級格式（驗收條件、實作與驗證步驟合併於 README）。兩份範本都含 placeholder 與說明用 HTML 註解，最終輸出前移除。


## 日期規範

新建立與本次修訂紀錄使用系統當日 `YYYY-MM-DD`；既有歷史日期保留，外部事件日期按實際發生時間記錄。預定窗口記未來的實際日期，不以今天代填。issue metadata 保留建立日期、分級、風險、狀態；常青文件另記最後驗證日期。

## 標記符號規範

任務使用 ✅ 已完成、⏳ 進行中、📝 待實作、🔄 重構中，或 project.md 指定的等價符號。完成狀態必須有對應證據。

## Agent 工作流程與時序保留 (Workflow & Timeline Tracking)

1. 從需求、對話與 workspace 取得目標，依規模與風險規劃；只澄清影響結果的缺項。
2. 依 acceptance.md 記錄已核准內容、初始文件與任務清單；任務只有一個權威來源。
3. 實作後在原任務項目寫入狀態與證據連結。README Timeline 只記建立、核准、規格修訂及結案等語意事件。
4. 當前驗收區塊與任務清單保持可執行的最新版；被推翻的分析保留帶日期的 NOTE，規格修訂前後差異交給 Git，Timeline 記決策來源。issue 文件不再增加檔尾 Changelog。
5. 依下節更新受影響的常青文件；結案後的 issue 保留歷史，後續需求另建 issue。

## 常青文件更新責任 (Evergreen Docs)

規劃與交付前讀 project.md 的「常青文件更新責任」，按變更觸發更新對應文件。有新的常青文件時一併登記觸發條件。常青文件描述當前系統，更新正文與最後驗證日期；issue 描述該次決策與交付歷程。
