# 驗收規格與核准

建立、修訂或查核驗收條件時讀本檔。流程契約由 [AGENTS.md](../AGENTS.md) 定義；本檔是核准的權威來源。

## 需求澄清與授權

先讀使用者需求、已核准計畫與本次對話。使用者已明確指定可觀察結果與範圍，或已接受具體方案時，記錄該原話、日期及對應驗收編號作為核准來源，直接推進相符內容。重排文字或選擇等價的實作／驗證命令不需再次核准。

只有會改變需求邊界、成功／失敗行為、安全範圍或必要驗證的缺項才詢問，詢問方式依下節逐題確認。使用者明確要求時才改用 Superpowers `brainstorming` 探索方案；已有共識時直接保留核准證據。

### 逐題確認

1. 列出待決策清單，依相依排序：前提已確定、會影響其他題的先問。能從程式碼、設定、文件或既有對話查到的事實自行查證；查證未完成時只延後依賴它的題目。
2. 每則訊息只問一題，編號並寫明問題、可選做法、建議答案與理由、影響的驗收編號。存在實質取捨才列多個做法，不為湊數創造替代方案。
3. 每次回答後重排清單：被答案涵蓋或已無關的題目移除，新出現的決策依相依插入。
4. 使用者明說「一起問」時，彼此獨立的題目可合併在同一則訊息，各題仍分別編號並附建議答案。
5. 清單清空即完成：每題都有答案，非阻塞未知已記入 README `## 待確認事項` 或寫成明說的假設。答案彼此牽動時，以一則總結列出決策與對應驗收編號請使用者確認；逐題答案已涵蓋結果與範圍時直接記錄。

回答「照建議」即接受該題建議答案。核准來源記原話、日期、題號、建議內容與對應驗收編號；解決的待確認事項同步更新狀態、結論與日期。

使用者沉默、時間經過、僅提供 issue ID 或「繼續」不構成新行為的核准；既有授權則持續有效。新增未授權行為與實質改規格才取得新的同意。

## 驗收標準的形式依規模決定，強度依風險決定

| 規模 | README 形式 |
|---|---|
| Small | `## 驗收條件`：穩定編號 AC-1、可觀察結果與可重複檢查方式；核准日期與來源 |
| Medium / Large | `## Gherkin 驗收劇本` 與 `## Gherkin 核准紀錄`：穩定 Scenario ID、Given / When / Then、核准 commit、來源與狀態 |

風險 Medium / High 時，輕量 AC 每項補失敗路徑，至少一項覆蓋最大風險，另記 `**核准 commit**`。高風險加強證據而不增加格式。既有 Small 已採 Gherkin 者依原形式查核；規模升級時轉換形式，但只有語意變更的條目需重新核准。

## 完整 Gherkin 的要求

Scenario 使用唯一且穩定的 ID（SCN-001 為範例，不限制前綴），描述外部行為，不綁內部函式或資料表。涵蓋主要成功路徑與已知重要失敗路徑；有共用前提或資料組合時可用 Background 或 Scenario Outline。

## Gherkin 核准紀錄

- **核准 commit**: 承載當次核准規格的提交；未提交先填 `待提交`，首次提交後回填。
- **核准來源**: 使用者明確要求或核准的原話與日期，可引用可追溯的 issue／對話紀錄。

| Scenario | 核准日期 | 狀態 |
|---|---|---|
| SCN-001 | YYYY-MM-DD | 已核准 |
| SCN-002 | - | 待核准 |

狀態為 `已核准`、`待核准`、`待重新核准`。表格與現存 Scenario 集合完全相等；狀態只讀本表，歷史敘述不改變判定。

所有 Scenario 同日一次核准可沿用既有單行「全部 Scenario 於 YYYY-MM-DD 核准」。出現分批或修訂時展開表格。相容舊單行格式時，其他區塊出現待核准字樣則先展開表格、核對真實核准來源，不把歷史字串直接當未核准。形式以核准區塊有無 `| Scenario | 核准日期 | 狀態 |` 表頭判定；摘要句與表並存時依表。

## 分批核准

已核准內容須涵蓋核心目標的主要成功與已知重要失敗路徑，才可開始實作；輕量 AC 須全部核准。待核准 Scenario 在 README 待確認事項寫明所等待的資訊。

只實作已核准、且相依條件均已滿足的 Task。其他 Scenario 待核准或待重新核准不阻塞無相依的 Task。新核准 Scenario 在 Large 計畫中尚無責任 Task 時，先補拆同一份計畫；修訂後的 Task 重新確認完成判準與證據是否仍有效。PR 前所有現存驗收條件都須已核准，或有逐項明列的豁免。

## 規格修訂的查核

需要核准 commit 的 issue，在實作前比對核准版本與**實際讀取的工作區**（包含已暫存及未暫存的最終內容）：

```bash
git diff "${approval_commit}" -- "docs/issues/issue-${issue_id}/README.md"
```

交付時另外確認 issue 文件與其他交付檔案均已提交，再以固定交付 HEAD 比對。未追蹤的新規格沒有 Git 比對基線，須先依來源完成核准與初始提交；`待提交` 不代表自動核准。

- 差異未改變條件、動作、結果或必要檢查：原核准有效；有規格措辭修訂才記 Timeline。
- 實質改變或增刪條件：只標記受影響項為 `待重新核准`；輕量 AC 在條目後加 `（待重新核准）`。重新核准後更新日期、狀態、核准來源與基線提交。
- Small + Low 無核准 commit，仍須對照核准原話，語意修改同樣需取得同意並記 Timeline。

rebase／squash／amend／cherry-pick **在合併前也可能改寫核准 SHA**。重寫前保存核准內容與來源；重寫後核對新提交的驗收區塊與原核准內容相符，才映射並回填新 SHA。缺少可驗證基線時停止依賴該核准的實作，從可追溯紀錄恢復或重新取得同意，不能挑目前 HEAD 當作已核准。

合併後核准 SHA 不再是實作 gate；以固定版本的規格與核准來源保留歷史，不為回填單獨製造提交。
