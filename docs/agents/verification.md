# 執行與驗證證據

實作或審查證據時讀本檔。核准依 [acceptance.md](acceptance.md)，本檔是測試、等價證據與假綠燈的權威來源。

## 雙迴圈追蹤

依驗收編號連結外部行為、底層行為與測試策略。計畫記錄可觀察層級與完成判準；實作時從現有驗證入口選擇具體路徑、命令與預期失敗原因。沒有 BDD runner 時，以標注驗收編號的整合／端對端測試承擔外迴圈；真正同層者依下方規則合併。

production code 包含原始碼、執行期設定、migration 與改變產品行為的資產。先取得與缺少目標行為直接相關的紅燈，再最小實作；語法錯誤、缺依賴或環境故障不是目標行為的紅燈。測試 fixture 與 Step Definitions 可先建立。

### 紅綠重構證據

**本檔以「紅綠重構證據」一詞指稱下列四段的完整集合**，其他文件與 skill 直接使用此詞，不再逐一展開：

1. 外迴圈紅燈
2. 單元測試紅燈
3. 最小實作後全綠
4. 重構後全綠

每一段都必須記錄驗收標準編號、實際命令、exit code 或結果摘要，以及與目標行為相關的失敗／成功原因。只有「測試已通過」的文字、狀態符號或 commit 存在，都不構成證據。四段缺任一段即為證據不完整。

**單迴圈合併**：任何規模的 Task，外迴圈與內迴圈若覆蓋同一可觀察層級、沒有額外整合責任，可合併紅燈，記錄「為何此層級已涵蓋本項行為，沒有遺漏另一層保障」。存在不同的整合／底層失敗面時保留雙迴圈。重構為 no-op 時，最小實作後綠燈可同時證明最終狀態，明列 no-op 理由即可，不增加相同測試執行。

### 假綠燈

**「假綠燈」指以任何方式製造出不代表行為正確的綠燈**，包含但不限於：

- 刪除、略過、弱化、註解、只執行部分或改寫既有測試
- mock 掉正在驗收的核心行為、硬編碼測試資料答案、使用無實際 assertion 的測試
- **同義反覆（tautological）**：斷言以**與被測程式碼相同的方式**重算期望值，於是 passes by construction——它永遠不可能與程式碼不一致，因此測不出任何東西

同義反覆是最隱蔽的一種，因為它的紅綠燈看起來完全正常。典型形態：

```
expect(add(a, b)).toBe(a + b)          // 用同一個算式驗同一個算式
expect(fmt(d)).toBe(d.toISOString())   // 斷言複製了實作
snapshot = 以手算重跑一次實作邏輯       // 手算路徑與程式碼路徑相同
```

**期望值必須來自獨立的真相來源**：已知良好的字面值、人工推導過的實例、規格原文、或另一條不共用實作的取得路徑。判斷方式是問——**這個斷言有沒有可能與程式碼意見不合？** 不可能，它就不是測試。

這與「觀測式驗收」的反向自檢是同一個機制的兩種形態：同義反覆是**斷言與實作不獨立**，觀測式假綠燈是**判準與失敗模式不相交**，兩者的綠燈都來自判準本身失效，而非行為正確。

假綠燈一律不得作為證據。測試契約只有在核准的行為已變更、能以證據證明測試錯誤，或使用者明確要求時才可修改，且必須記錄真實理由——把上述任一情況記錄成「測試通過」即構成不實回報。

### 證據持久力（與假綠燈分開判定）

**假綠燈的判準是「這次的綠燈是否代表行為正確」，不是「這個綠燈日後是否還擋得住回歸」。** 後者稱為**證據持久力**，是不同的問題，必須用不同的標籤判定：

- 探針或斷言綁在被測程式碼自身的易變細節上（特定字串、日誌訊息、行號），改動者順手改掉那行，守門就消失
- 覆蓋面窄到容易繞過，或斷言只驗證了行為的代理指標而非行為本身

證據持久力不足**不構成假綠燈**：只要紅燈為真、綠燈確實由目標行為驅動，證據對本次驗收就是有效的。`review` 將其列為建議層級（SHOULD FIX / NICE TO HAVE）並提出更穩固的替代斷言，本次驗收的判定維持通過。

**實作者主動揭露測試限制，永遠不構成缺失。** 這條是前一條的前提：若誠實揭露會讓自己被歸進「假綠燈」這種帶指控意味的標籤，理性的選擇就會變成不揭露——一條讓誠實比沉默更危險的規則，正在傷害它本來要保護的東西。揭露應被視為證據品質的一部分，而非扣分項。

## 觀測式驗收（判準為生產環境觀測時）

部分驗收標準的最終判準不是測試，而是**生產環境的實地觀測**（排程執行後的計數、逾時數、分位數、健康快照、對帳結果）。這類證據沒有紅燈基線可對照——測試至少會先紅一次證明它抓得到問題，觀測判準不會，因此**判準本身失效時看起來與行為正確完全一樣**。

**反向自檢（每項觀測式 AC 必答）**：

> **「若這件事失敗了，這個判準會不會仍然是綠的？」**

答不出「不會」，就不算通過，必須改判準或補判準。這道自檢針對的失效不是層級選錯、也不是證據持久力不足，而是**判準與失敗模式不相交**——例如以「戳記數量」驗收派工是否完成，而未派工的目標保留舊戳記，於是漏派時計數依然漂亮；或以查詢結果為零判定「已清乾淨」，而零其實來自查詢本身寫錯。這兩類都是**綠燈來自判準失效，而非行為正確**，屬於「假綠燈」。

**必要步驟**：

1. **先驗證判準本身**：在取得驗收數據前，以已知結果的對照組（歷史區間、已知樣本、刻意構造的失敗情境）確認取數管道與判準確實反映真實狀態。未經此步的觀測數據不得作為證據。
2. **寫出失敗時的可觀察差異**：明確記錄「行為失敗時，這個判準會呈現什麼」，並確認與成功時不同。
3. **記錄實際觀測**：取數時間、範圍、命令或查詢原文、實際數值，以及對照組結果。

觀測式 AC 依賴外部時間窗（每週排程、月結、對帳日）時，依 [AGENTS.md 的合法狀態](../AGENTS.md#合法的中間狀態與終態)記錄預定窗口，不視為停滯。

## 不改變可觀察行為的任務

紅燈要求只適用於會改變可觀察行為的任務。下列兩類依定義就不該產生失敗測試，改用等價證據：

- **純重構**（搬移、改名、抽取、格式化）：記錄「變更前」與「變更後」執行**同一組**既有測試的實際命令與全綠輸出。既有測試不足以覆蓋被重構的行為時，先補上 characterization test 並取得綠燈，再開始重構。
- **純文件、排版或無可執行行為**：以可重複的靜態檢查或明確手動步驟替代，記錄不適用理由與實際結果。

在計畫中將任務標為「不改變可觀察行為」，等同承諾其 diff 不含行為變更；review 會據此查核，發現行為變更時退回補齊紅燈證據。


## 證據重用

每筆證據保存在原任務項目或可跨 session 讀取的 CI／log artifact，記命令、結果、時間、驗收編號、被測提交或工作區狀態。多個條件共用一次測試時，各自映射到同一證據。交付前確認其版本、設定、環境與待交付內容一致；有差異或時效需求才重跑。重構階段由 execute-task 調用 code-simplify 一次；沒有可改善內容時記 no-op 並沿用同一份有效綠燈證據。
