# 步驟 5：「近期對話」配對規則在正式資料上的盤點

- **日期**：2026-10-07
- **對應**：SCN-007；TBD-3
- **資料**：正式部署 `moltbot.db` 的複本，以 `sqlite3 -readonly <正式檔> ".backup <暫存檔>"` 取得，放在 repo 之外，盤點完已刪除。repo 是公開的，所以本檔只記時間、數量與類別，不記任何對話內容。
- **範圍**：2026-02-10 11:46 至 2026-10-07 09:20（UTC+8），共 3,186 筆：user 300 筆、model 2,886 筆，只有一位使用者。

## 規則

user 訊息一律算聊天；model 訊息只有在同一使用者的前一筆（依 `timestamp, id` 排序）是 user 時，才算聊天回覆。查詢就是 `MemoryManager.getRecentConversation()` 的 SQL（SQLite 3.46.1 的 `LAG()` 視窗函式）。

## 結果

| 項目 | 筆數 |
|---|---|
| 判為聊天回覆的 model | 297 |
| 被排除的 model | 2,589 |
| user 後面接著 user，或沒有下一筆（失敗的回合不寫入回覆） | 3 |

被排除的 model 中，最常見的開頭依序是市場分析、每日摘要、排程逾時或失敗通知、追蹤提醒、`✨ 無待辦。`，與排程輸出的樣態相符。

### 誤判

找誤判的方法：列出「user 之後連續兩則 model，而且第二則落在 user 之後 35 分鐘內」的情況（聊天回合逾時為 30 分鐘），共 106 筆，逐筆比對兩則 model 的開頭與時間差。另外把判為回覆、但開頭帶排程標記（`📅 [`、`🔔 [`、`🔍 [`、`⏱️ 排程`、`❌ 排程`、`✨ 無待辦`、`✅ [追蹤`）的訊息全部列出，共 3 筆，都已包含在上面的 106 筆中。

| 判定 | 筆數 | 說明 |
|---|---|---|
| 正確 | 92 | 第一則是回覆，第二則是排程或同一回合的重複輸出 |
| 確定誤判：排程被當成回覆，真正的回覆被排除 | 8 | 2026-02-12 13:58、02-12 15:20、03-02 10:30、05-18 11:00、05-26 15:59、06-01 16:01、06-03 11:00、06-23 14:01。其中 06-01 16:01 的「回覆」在使用者訊息後 2 秒寫入，不可能是聊天回覆 |
| 確定誤判：聊天沒有回覆，排程失敗通知被當成回覆 | 1 | 2026-06-01 15:01 |
| 無法判斷 | 5 | 2026-02-25 11:23、02-25 14:27、03-05 09:29、05-04 10:01、06-09 15:51。兩則都像回覆，或使用者要求重跑排程 |

確定誤判 9 筆，佔 297 個聊天回合的 3.0%；把無法判斷的 5 筆都算成誤判，則是 14 筆、4.7%。

### 對照：現行規則與新規則的「近期對話」

以複本最後的狀態取最近 10 筆：

| 規則 | 排程輸出 | 聊天訊息 | 涵蓋期間 |
|---|---|---|---|
| 現行（最近 10 筆，不分來源） | 10 | 0 | 2026-10-06 20:04 至 10-07 09:20 |
| 新規則 | 0 | 10（5 則 user、5 則回覆） | 2026-09-09 21:08 至 10-03 09:05 |

## 結論（TBD-3）

誤判率約 3%（最壞 4.7%），發生在聊天回合進行中剛好有排程寫入的時候，每次誤判只讓一則回覆的位置換成一段排程片段（截到 180 字）。加上 SCN-006，「近期對話」只在開新 session 的回合注入。現行規則下這一段 100% 是排程輸出，相比之下新規則已經足夠，**不新增來源欄位**，規模維持 Medium。這個限制記在 `getRecentConversation()` 的註解與測試中。

反向自檢：如果新規則沒有生效，最近 10 筆會和現行規則相同，全是排程輸出；對照表顯示兩者完全不同，所以這個判準抓得到失敗。
