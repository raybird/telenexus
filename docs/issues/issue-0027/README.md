# Issue 0027 - Telegram 回覆的 Markdown 轉換會丟掉子清單、編號與標題層級 (Small)

GitHub：[#27](https://github.com/raybird/telenexus/issues/27)

## 概述

`src/telegram/render/markdown-v2.ts` 把模型回覆轉成 Telegram MarkdownV2。清單項目只轉其中的段落，其他節點（子清單、程式碼、引言）回傳空字串；最上層與行內不認得的節點也回傳空字串，沒有任何紀錄。

2026-11-13 以正式部署近 60 天的 873 則模型回覆統計：

| 情況 | 則數 | 現在的結果 |
|---|---|---|
| 清單項目裡有子清單 | 115（13%） | 子清單整段消失，例如市場報告第 1 點底下的支撐與阻力價位全部不見 |
| 有編號的清單 | 405（46%） | `1. 2. 3.` 全部變成 `•` |
| 標題 | 291 | `#`～`######` 都變成同樣的粗體 |
| 刪除線、勾選框、圖片、HTML | 0 | 不處理（見「不在範圍內」） |

近 7 天沒有 MarkdownV2 解析失敗而退回純文字的紀錄：跳脫本身穩定，問題在轉換器漏處理節點。

**不在範圍內**：
- 模型的過程敘述與結論分開、過程摺疊：另開 [#28](https://github.com/raybird/telenexus/issues/28)。
- GFM（刪除線、勾選框）：近 60 天 0 則；加上 remark-gfm 預設會把單個 `~` 當刪除線，`$80,000~81,300`、`10-29~30` 這類常見寫法會被誤判。
- 表格的轉換方式（`TelegramConnector.normalizeMarkdownTables()` 在轉換前已處理）、4096 字切段、HTML 模式的 `markdownToHtml()`。

## 驗收條件

1. **AC-1**：子清單依層級輸出，不再消失。第 1 層用 `•`、不縮排；每多一層行首多 2 個空白，第 2 層用 `◦`，第 3 層以上用 `▪`。編號清單在任何一層都改用編號，縮排規則相同。同一項目的第二段起各自另起一行，縮排與該項目的符號相同（第 1 層不縮排）。 — 檢查方式：`npx tsx --test tests/telegram/render-markdown-v2.test.ts`，fixture 含三層混合清單（無序套有序、有序套無序）。
   - 失敗路徑：任何一層的項目文字沒出現在輸出裡，或層級縮排與上述不符，即失敗。
2. **AC-2**：有編號的清單保留原文的起始號碼並依序遞增，號碼後的 `.` 跳脫成 `\.`；例如原文從 `3.` 開始，輸出就是 `3\.`、`4\.`。 — 檢查方式：同 AC-1 的測試檔，含從 1 開始與從 3 開始兩種清單。
   - 失敗路徑：號碼被換成 `•`、號碼重新從 1 起算，或 `.` 沒有跳脫，即失敗。
3. **AC-3**：`#`、`##` 標題輸出為粗體加底線（`*__標題__*`），`###`～`######` 只用粗體（`*標題*`），與前後區塊之間各空一行。 — 檢查方式：同 AC-1 的測試檔，六個層級各一個標題。
   - 失敗路徑：兩組層級輸出相同，即失敗。
4. **AC-4**：轉換不丟內容。清單項目與引言裡的程式碼區塊、引言、子清單、標題照常輸出；轉換器不認得的區塊或行內節點（例如 HTML、圖片），以原文跳脫後輸出，不輸出空字串。唯一的例外是 `<think>`、`</think>` 兩個標籤本身不輸出，標籤前後的文字照常輸出。 — 檢查方式：
   - 測試：fixture 涵蓋上述每一種節點；斷言把輸出去掉 MarkdownV2 跳脫與格式符號後，原文的每個字詞都還在（`<think>`、`</think>` 除外）。另一個 fixture 含 `</think>`，斷言輸出沒有這個標籤、前後文字都在。
   - 實際資料：本機以正式部署近 60 天的回覆跑新舊轉換器，統計輸出缺字詞的則數，`<think>`、`</think>` 不算缺。舊版的基線是 130 則（[步驟 2](evidence/step2-corpus-baseline.md)），新版必須是 0。原文不提交，只把統計數字寫進證據。
   - 失敗路徑：任何 fixture 或任何一則實際回覆的輸出缺少原文字詞，或輸出含 `<think>`、`</think>`，即失敗。
5. **AC-5**：Telegram 接受新的輸出，排版照 AC-1～AC-3 顯示。 — 檢查方式：用正式 bot 的 token 直接呼叫 Bot API `sendMessage`（`parse_mode: MarkdownV2`，不 poll，不停正式服務），送約 10 則樣本到維護者的聊天，樣本涵蓋 AC-1～AC-4 的每一種結構；全部回 `ok: true`，再由使用者在手機上確認縮排與編號看得出來。
   - 失敗路徑：任何一則回 400（例如 `can't parse entities`），或使用者看到縮排被吃掉、層級分不出來，即失敗。
6. **AC-6**：不含子清單、編號清單、標題，也沒有清單項目或引言裡非段落區塊的回覆，新舊輸出逐字相同；既有 Telegram 轉換、切段與串流收尾測試全部通過。 — 檢查方式：AC-4 的實際資料對照同時比對這類回覆的新舊輸出；`npx tsx --test tests/telegram/`。
   - 失敗路徑：這類回覆有任何一則新舊輸出不同，或既有測試失敗，即失敗。

## 風險與首要驗證

- **最大風險**：Telegram 不接受新的輸出或不照預期顯示。子清單靠行首空白縮排，Telegram 會不會保留還沒驗證；號碼的 `.` 只要漏跳脫一處，Telegram 就會拒收整則，連接器改送純文字，所有格式一起消失。
- **風險等級與理由**：Medium。失敗時連接器會退回純文字，內容不會丟，影響有限；但縮排能不能顯示是決定 AC-1 做法的重要未知。
- **首要驗證**：動工前手寫 3 則 MarkdownV2（三層縮排的無序清單、跳脫過的編號清單、粗體加底線的標題），用正式 bot 的 token 呼叫 `sendMessage` 送到維護者的聊天。
- **選擇理由**：行首空白會不會保留只能由 Telegram 本身回答，單元測試答不了；先送樣本，若空白被吃掉，可以在實作前改縮排做法，不必重做。
- **完成證據**：3 則都回 `ok: true`，使用者在手機上確認看得出縮排。
