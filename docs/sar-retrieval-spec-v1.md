# 📜 Summary-Aware Retrieval (SAR) 規格草案 v1.0

## 1. 核心目標 (Core Objectives)

- **跨越斷層**：確保 AI 始終能看見歷史中的「重大決策點」，即便對話已進行數千筆。
- **效率優化**：減少為了找回背景資訊而進行的重複檢索，降低 Token 內耗。
- **因果對齊**：使 AI 的回答始終基於已標記的「營運憲法」與「技術地板」。

## 2. 檢索架構 (Architectural Flow)

目前的檢索是單線性的（抓取最近 N 筆）。SAR 將改為 **「分層混合檢索」**：

### 階層一：即時上下文 (Immediate Context)

- **範圍**：最近 10 則原始對話。
- **目的**：維持當前對話的流暢感與語氣連貫性。

### 階層二：因果錨點 (Causal Anchors)

- **範圍**：資料庫中所有 `summary` 欄位不為空且標記為 `CRITICAL` 的紀錄。
- **機制**：將這些摘要壓縮後作為 `System Instruction` 或 `Memory Injection` 注入 AI 的開頭。
- **內容**：例如「2026-03-18：Docker 重啟，Git 身份需透過 bootstrap.sh 修復」。

### 階層三：動態語意補全 (Semantic Refinement)

- **範圍**：利用 `messages_fts` 進行全文檢索。
- **觸發點**：當 User 提及特定專案關鍵字（如 "WebDota"、"Memoria"）時，自動抓取該專案相關的歷史摘要。

## 3. 資料庫欄位規訓 (DB Schema Hardening)

為了支援 SAR，建議在 `messages` 表中增加以下欄位：

- **`impact_level` (INTEGER)**: 標記摘要的重要性（1: 一般, 2: 重要, 3: 營運憲法級）。
- **`tags` (TEXT)**: 標記專案分類（如 `webdota`, `crypto`, `sys_admin`），便於階層三的動態補全。

## 4. 虛擬代碼實作預演 (Pseudo-code)

```typescript
async function getContextForAI(userId: string) {
  // 1. 抓取最重要的 5 個因果錨點 (憲法級)
  const anchors = db
    .prepare(
      'SELECT summary FROM messages WHERE summary IS NOT NULL AND impact_level >= 2 ORDER BY timestamp DESC LIMIT 5'
    )
    .all();

  // 2. 抓取最近 10 則原始對話 (連貫性)
  const recents = db
    .prepare(
      'SELECT role, content FROM messages WHERE user_id = ? ORDER BY timestamp DESC LIMIT 10'
    )
    .all();

  // 3. 合併為 Context 傳遞給 Gemini
  return {
    system_reinforcement: '核心決策回顧: ' + anchors.join('; '),
    conversation_history: recents.reverse()
  };
}
```

## 5. 預期效益

- **記憶深度**：從「20 筆」擴展到「全量因果感知」。
- **因果穩定性**：重啟後 AI 會立刻說「我知道現在 Git 身份丟了，請執行 bootstrap.sh」，而不是問「你是誰」。
